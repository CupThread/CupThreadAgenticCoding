# Endpoint Contract Details

Reference detail for the `cupthread-api` skill, split out of `SKILL.md` so the
skill stays under the agent-skill size budget (issue #318). The live OpenAPI 3.1
spec (<https://api.cupthread.com/api/v1/openapi.json>) remains the authoritative
contract; these files mirror the shipped behavior behind it.

## Key Public & SDK Endpoints

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/v1/public/config/:appKey` | `GET` | Fetches the `PublicAppConfig`: app metadata, store/website links (`websiteUrl`), branding flags (`hideSiteBranding`), enabled platforms, anonymous-access settings (`allowAnonymousRoadmap`, `allowAnonymousVote`, `allowAnonymousFeedback`, `allowAnonymousChangelog`, and the `requireAnonymousVoteTurnstile` SEC-846 vote-verification gate), the optional `allowedEmbedOrigins` embed allowlist (SEC-518) — present only when the tenant configured portal embedding (an empty array is never returned): at most 10 exact `https://` origins (no path, query, fragment, userinfo, or wildcard host; an optional non-443 port is allowed) that may embed the app's public portal pages in an iframe (`frame-ancestors`); when the field is absent, embedding is disabled for the app everywhere — and the always-served `sdk` object (`SdkAppearance`, SaaS #1235): `theme` (one of `system`/`light`/`dark`/`midnight`/`ocean`/`forest`/`sunset`/`candy`, default `system`), `features` (`feedback`, `featureRequests`, `roadmap`, `changelog` booleans, all default `true`), and `changelogOverlay` copy (`title` 1–80, `subtitle` ≤240, `entryCount` 1–10, `primaryButton`/`closeButton` 1–40; defaults "What's New", "", 3, "Continue", "Close"). Tenants who never touched the theme editor get those defaults. Private apps and unknown keys both fail closed with `404 {"error": "App not found"}` (SEC-37). Rate limited per client IP at 60 requests/minute (`PUBLIC_CONFIG_RATE_LIMITER`); the spend is the first statement, before cache or lookup, so an over-budget caller sees `429 {"error": "Too many requests. Please try again shortly."}` with no D1 read. |
| `/api/v1/public/workspaces/:workspaceSlug/apps/:appSlug/config` | `GET` | Same `PublicAppConfig` (including `allowedEmbedOrigins`) resolved by workspace and app slugs instead of app key; the same fail-closed `404` applies to private apps. Same dedicated 60/minute config limiter, spent first. |
| `/api/v1/public/showcase` | `GET` | Public app showcase (alias `GET /api/v1/public/apps`), newest first, `{apps, total}`. `limit` default 50, max 100. `offset` above 5000 is clamped to 5000 and still returns `200` — it is not an error. Rate limited per client IP at 60 requests/minute (`PUBLIC_READ_RATE_LIMITER`, generic `429` JSON); the spend is the first statement. That bucket is shared with the public columns, versions, changelog, and comment-thread reads. |
| `/api/v1/public/columns/:appKey` | `GET` | Roadmap Kanban columns sorted by position. Apps with anonymous roadmap view disabled answer `401` `authentication_required` (PRIV-12) instead of the column list — see [Per-App Anonymous-Access Enforcement (PRIV-12)](rate-limits-and-cache.md#per-app-anonymous-access-enforcement-priv-12). An unknown `appKey` and a known app with public access disabled both answer the same uniform `404 {"error": "App not found"}` (existence hiding, SaaS #1165/#1171) — the negative response is short-TTL cached like the config endpoints, so clients must no longer read `403` as "the app exists but has public features disabled". Rate limited per client IP (`429`, shared 60/min public-read bucket); anonymous `200`s may be served from a 30-second shared cache — see [Public Board Read Limits and Shared Cache](rate-limits-and-cache.md#public-board-read-limits-and-shared-cache). |
| `/api/v1/public/versions/:appKey` | `GET` | Release versions sorted by position. Only rows whose `released` flag is true are listed (PROD-32) — unreleased versions stay console-private until a developer marks them released, and a request bound to an unreleased version still shows on the board with its version simply absent from this list. Same `401` `authentication_required` (PRIV-12) on sign-in-only roadmaps as the columns route. Same uniform `404 {"error": "App not found"}` for an unknown `appKey` and a known app with public access disabled (existence hiding, SaaS #1165/#1171, short-TTL negative-cached). Same 60/min `429` and 30-second anonymous cache as the columns route. |
| `/api/v1/public/apps/:appKey/changelog` | `GET` | Published release notes and changelog items. Cursor-paginated: `limit` (integer, 1–100, default 100) and opaque `cursor` (from the previous `nextCursor`); returns `{entries, hasMore, nextCursor}` — the envelope always emits all three keys, with `hasMore: false` and `nextCursor: null` on the last page. Each entry is the corrected `ChangelogEntry` schema (SaaS #1226 / PR #1273): `{id, title, body, versionLabel, publishedAt, linkedRequests}`, all six required — no `appId` (a workspace-internal identifier the public feed never serves), the version field is the operator's free-form `versionLabel` (nullable string, **not** `versionNumber`), and `linkedRequests` is an always-present array of `{id, title}` approved feature-request summaries (empty for callers who fail the roadmap visibility gate — it is required, not optional). Deterministic errors: `400` `{"error": "Invalid cursor"}` for a malformed `cursor`, `401` `authentication_required` when the app's `allowAnonymousChangelog` is false and no end-user session is present, `403` `{"error": "Public surfaces are disabled for this app"}` for a private app, `404` for an unknown `appKey`, plus `429` when the rate budget is spent. Rate limited per client IP (`429`, shared 60/min public-read bucket). Only anonymous `200`s enter the 30-second shared cache; a Clerk session skips it and keeps session-dependent linked-request titles — see [Public Board Read Limits and Shared Cache](rate-limits-and-cache.md#public-board-read-limits-and-shared-cache). |
| `/api/v1/public/apps/:appKey/changelog/subscribe` | `POST` | Subscribe an email to changelog updates (double opt-in). Success is always `201 {"subscribed": true}` — the former `alreadySubscribed` field was removed, so the response never reveals prior state. The address starts *pending* and a single-use confirmation email is sent (resends within a 15-minute cooldown return `201` without dispatching a duplicate email). The request body (`SubscribeChangelogInput`) accepts an optional `turnstileToken` (string, 10–2048 chars): when the server enforces Turnstile human verification, anonymous subscription requests require a valid token, and one that is missing or fails verification answers `403 {"error": "Human verification failed. Please try again.", "code": "turnstile_verification_failed"}` — signed-in callers subscribing with their session's verified email address are exempt. Changelogs with anonymous access disabled reject anonymous calls with `401` `authentication_required` and bind signed-in calls to the session's verified address: a body `email` that is not one of them fails with `403 {"error": …, "code": "email_not_verified"}` (PRIV-12). Rate limited per client IP (`429`). |
| `/api/v1/public/apps/:appKey/changelog/confirm` | `GET` | **Non-destructive** confirmation interstitial (SEC-35): validates the emailed token (read-only) and renders an HTML page whose form POSTs the token; a GET **never modifies** the subscription, so email security gateways (SafeLinks/Proofpoint/Mimecast URL detonation) and link prefetchers cannot consume the single-use token. JSON-only clients (`Accept: application/json` without `text/html`) get `405 {"error": "GET does not confirm subscription. POST the token to this endpoint to confirm."}` with `Allow: POST`. Missing token → `400 {"error": "Missing confirmation token"}`; unknown/expired/already-used tokens → `400 {"error": "Invalid or expired confirmation token"}` (uniform, no oracle). A private app returns `403 {"error": "Public surfaces are disabled for this app"}` before the token is considered. Expired confirmation tokens stay this `400` — the unsubscribe grace in #635 does not apply. Rate limited per client IP (`429`). |
| `/api/v1/public/apps/:appKey/changelog/confirm` | `POST` | **The only mutating double-opt-in confirmation** (SEC-35): consumes the single-use emailed token and flips the subscription to *confirmed*. Token accepted via query string (`?token=...`), JSON body `{"token": "..."}`, or the interstitial form's `token` field (urlencoded/multipart) — query wins when several are present. Replays and expired tokens fail uniformly with `400 {"error": "Invalid or expired confirmation token"}` (single-use, no oracle). A private app returns `403 {"error": "Public surfaces are disabled for this app"}`. Browser form submissions (`Accept: text/html`) get the HTML confirmation landing page; everything else gets `{"confirmed": true}`. Rate limited per client IP (`429`). |
| `/api/v1/public/apps/:appKey/changelog/unsubscribe` | `GET` | **Non-destructive** confirmation interstitial (PROD-20, #635): renders an HTML form that POSTs the token; the subscription is never modified. Email security gateways and link prefetchers that GET this URL cause no side effect. A signature that matches this app is accepted after `exp` and when public surfaces are disabled. JSON-only clients (`Accept: application/json` without `text/html`) get `405 {"error": "GET does not unsubscribe. POST the token to this endpoint to unsubscribe."}` with `Allow: POST`. On a public app, a missing token is `400 {"error": "Missing unsubscribe token"}` and a token that does not verify is `400 {"error": "Invalid or expired unsubscribe token"}`. On a private app, a missing or non-matching token is `403 {"error": "Public surfaces are disabled for this app"}`. Rate limited per client IP (`429`). See [Changelog Unsubscribe on Private Apps and After Expiry (#635)](email-subscriptions.md#changelog-unsubscribe-on-private-apps-and-after-expiry-635). |
| `/api/v1/public/apps/:appKey/changelog/unsubscribe` | `POST` | The only destructive path (also serves RFC 8058 `List-Unsubscribe=One-Click`, #635): token via query string, JSON body `{"token": "..."}`, or form field. The bare-email unsubscribe (`{"email": "..."}`) was **removed**. A signature that matches this app returns `200 {"unsubscribed": true}` even after `exp` and when public surfaces are disabled (HTML landing page only when `Accept` includes `text/html`). On a public app, no token is `400 {"error": "An unsubscribe token is required"}` and a token that does not verify is `400 {"error": "Invalid or expired unsubscribe token"}` — an authentic signature is not that `400`. On a private app, a missing or non-matching token is `403 {"error": "Public surfaces are disabled for this app"}`. Rate limited per client IP (`429`): a query-string token draws from the dedicated 300/min one-click budget (PRIV-08) before the body is read; a POST without a query token stays on the shared 10/min public-write bucket. See [Changelog Unsubscribe on Private Apps and After Expiry (#635)](email-subscriptions.md#changelog-unsubscribe-on-private-apps-and-after-expiry-635). |
| `/api/v1/public/digest/unsubscribe` | `GET` | **Non-destructive** weekly-digest unsubscribe confirmation interstitial (PRIV-07): validates the signed token and renders an HTML form that POSTs it back; notification preferences are never modified by a GET. JSON-only clients (`Accept: application/json` without `text/html`) get `405` with `Allow: POST`. Missing token → `400 {"error": "Missing unsubscribe token"}`; invalid/expired → `400 {"error": "Invalid or expired unsubscribe token"}`. Rate limited per client IP (`429`, shared 10/min public-write bucket). See [Weekly Digest Unsubscribe (PRIV-07)](email-subscriptions.md#weekly-digest-unsubscribe-priv-07). |
| `/api/v1/public/digest/unsubscribe` | `POST` | The only destructive digest path (serves RFC 8058 `List-Unsubscribe=One-Click`): token via query string (takes precedence), JSON body `{"token": "..."}`, or a `token` form field. Success → `{"unsubscribed": true}` (HTML landing page when `Accept` includes `text/html`); replay is idempotent. `400 {"error": "An unsubscribe token is required"}` without a token; `400 {"error": "Invalid or expired unsubscribe token"}` for bad ones. Clears only the workspace `weekly.digest` **email** event — inbox notifications are unchanged. Rate limited per client IP (`429`): a query-string token draws from the dedicated 300/min one-click budget (PRIV-08) before the body is read; a POST without a query token stays on the shared 10/min public-write bucket. See [Weekly Digest Unsubscribe (PRIV-07)](email-subscriptions.md#weekly-digest-unsubscribe-priv-07). |
| `/api/v1/public/apps/:appKey/user` | `PUT` | Update host app user attributes (paying, MRR, currency). Bodies reporting any payment attribute (`isPaying`, `mrr`, `plan`, `currency` — an explicit `null` counts) must carry an HMAC-signed `signature` + `timestamp`; a signed update that omits `currency` preserves the stored currency instead of coercing it to `USD` (DATA-07). See [SDK Payment-Attribute Signing (DATA-03)](payment-attribute-signing.md#sdk-payment-attribute-signing-data-03). Rate limited per client IP: 60 requests/minute, `429` on bursts — retry with exponential backoff when syncing many users behind one shared IP. |
| `/api/v1/feature-requests` | `GET` | List/search feature requests (`limit` 1–200, default 50; legacy `offset`; `versionId`; `q`). Cursor-paginated (DATA-01): opaque `cursor` from the previous `nextCursor`; returns `{requests, total, hasMore, nextCursor}` with `nextCursor` `null` on the last page; malformed cursors fail with `400` `{"error": "Invalid cursor"}`. `offset` above 10000 is clamped to 10000 and still returns `200`. Plain listings (no `q`) are rate limited per client IP at 60 requests/minute (`BOARD_LIST_RATE_LIMITER`, generic `429` JSON); searches stay on a separate 30/minute bucket (`429 {"error": "Too many searches. Please try again shortly."}`). Boards with anonymous roadmap view disabled answer `401` `authentication_required` to unauthenticated reads. An unknown `appKey` and a known app with public access disabled both answer the same uniform `404 {"error": "App not found"}` (existence hiding, SaaS #1165/#1171) — the disabled-app case, previously an undocumented `403`, is no longer distinguishable from an unknown app. Personalize with the **`X-User-Token` header**; the legacy `?userToken=` query parameter is deprecated (see [End-User Token Header & Identity Linking (SEC-12)](user-identity-and-privacy.md#end-user-token-header--identity-linking-sec-12)). |
| `/api/v1/feature-requests/:id` | `GET` | Read one approved feature request by id (SaaS #713: the deep-link read behind the web portal's shareable `/{workspaceSlug}/{appSlug}/requests/{requestId}` URLs) — a client holding a single id (deep link, ship-notify email, notification payload) no longer fetches the whole board to resolve it. The `200` body is `{request}` holding the **same record shape the board listing serves per item**: `id`, `appId`, `title`, `description`, status/column fields, release version label, `voteCount` (live votes plus imported historical total), `importedVotes`, `commentCount`, `recentCommenters`, `createdAt`/`updatedAt` (SaaS #1320 / PR #1323: neither this endpoint nor `GET /api/v1/feature-requests` serves the ten undocumented tenant-internal keys `importSource`, `importRef`, `githubIssueId`, `githubIssueNumber`, `githubIssueUrl`, `githubDiscussionId`, `githubDiscussionNumber`, `githubDiscussionUrl`, `githubLastSyncedAt`, or `githubSyncStatus` — those belong to the Console admin surface only). Optional `X-User-Token` header (UUID, same header as the board listing — see [End-User Token Header & Identity Linking (SEC-12)](user-identity-and-privacy.md#end-user-token-header--identity-linking-sec-12)) personalizes the record: `hasVoted` reflects that token's ballot and `isOwnRequest` marks the caller's own request; a malformed token personalizes nothing (silently treated as absent, no error) and a signed-in Clerk session personalizes from the caller's identity instead. Gates mirror the board listing and comment thread, in order: per-client-IP public-read rate limit first (`429`, shared 60/min `PUBLIC_READ_RATE_LIMITER` bucket — the spend is the first statement, before any lookup), then existence hiding — a missing id, an id on an app with public access disabled or deactivated, and an **unapproved** request all answer the same uniform `404 {"error": "Feature request not found"}` (the unapproved requester's own token does **not** un-hide it: deep links resolve approved records only), then the PRIV-12 gate — a board with anonymous roadmap view disabled answers `401` `authentication_required` to anonymous callers (checked before the approved check, so while the flag is off both approved and pending ids answer `401`, never a `404`/`200` distinction). Caching: a fully anonymous `200` is identity-independent and may come from the same 30-second shared cache as the other board reads; a token- or session-bearing caller skips the cache in both directions, so a personalized body is never served stale or cross-user — see [Public Board Read Limits and Shared Cache](rate-limits-and-cache.md#public-board-read-limits-and-shared-cache) and [Per-App Anonymous-Access Enforcement (PRIV-12)](rate-limits-and-cache.md#per-app-anonymous-access-enforcement-priv-12). |
| `/api/v1/feature-requests` | `POST` | Submit (propose) a new feature request. Body: `appKey` (8–128 chars, required), `title` (3–160, required), `description` (5–5000, required — image embeds are stripped at intake, PRIV-11), optional `requesterName` (1–120), `requesterToken` (UUID), and `turnstileToken` (10–2048, required only when the API has a Turnstile secret configured); there is no `requesterEmail` field. The requester token may be sent in the body field `requesterToken` **or** the `X-User-Token` header (SaaS #834): the body field wins when both are present, a present-but-invalid body field still fails with `400 Validation failed`, and a payload with **neither** source answers the same `400` shape with `details.fieldErrors.requesterToken: ["Required — send the token in the JSON body or the X-User-Token header"]`. Success answers `201` with the two-field intake receipt `FeatureRequestSubmissionCreated` (SaaS #1105): `{featureRequestId, pending}`, both required — `pending` is the boolean moderation flag, `true` while the request awaits approval (every public submission starts unapproved), so a strict client must not model the full public `FeatureRequest` board record here. Gates in order: 256 KB body budget (SEC-36), per-client-IP public-submit rate limit (`429 {"error": "Too many submissions. Please try again shortly."}`), Turnstile verification (`403`), workspace tier check (`402` `tier_limit_submissions`/`subscription_inactive`), and a board with anonymous feedback disabled answers `401` `authentication_required` to anonymous callers. |
| `/api/v1/feature-requests/:id/vote` | `POST` | Cast the caller's vote — insert-only (PROD-36), no longer a toggle. Repeating the request is idempotent: it leaves an existing vote in place and re-serves the same `{voted: true, voteCount}` body, so a retry after a network error can no longer cancel the vote; `DELETE` is the only way to remove it. Body `{appKey, userToken}` plus optional `shipNotifyEmail` (email string, max 254) and optional `turnstileToken` (string, 10–2048 chars, `VoteFeatureRequestInput`) — see [Ship-notification opt-in on vote](voting-and-submissions.md#ship-notification-opt-in-on-vote). When the server enforces Turnstile human verification, an anonymous voter that opts in via `shipNotifyEmail` should supply a verified token: on a board whose public config sets `requireAnonymousVoteTurnstile: true`, a missing or failed token rejects the vote outright with the SEC-846 `403` (`turnstile_required` / `turnstile_verification_failed`, see [Turnstile-gated anonymous vote (SEC-846, #243)](voting-and-submissions.md#turnstile-gated-anonymous-vote-sec-846-243)); on boards without that flag, a missing or failed token leaves the vote itself at `{voted: true, voteCount}` unchanged while the ship-notification opt-in is silently suppressed — no confirmation email is sent — to protect recipients from abuse. The `userToken` may equally be sent in the `X-User-Token` header (SaaS #834): the body field wins when both are present, a present-but-invalid body field still fails with `400 Validation failed`, and a payload with **neither** source answers the same `400` shape with `details.fieldErrors.userToken: ["Required — send the token in the JSON body or the X-User-Token header"]` — so a header-only vote body carries just `appKey`. Returns `{voted, voteCount}` where `voteCount` includes imported historical votes; omitting `shipNotifyEmail` leaves that shape unchanged. Rate limited per client IP — 20 requests/minute with a vote-specific `429` body (see [Rate Limiting](rate-limits-and-cache.md#rate-limiting-429-too-many-requests)). Existence hiding (SaaS #1165/#1171): an unknown `appKey` and a known app with public access disabled both answer `404 {"error": "App not found"}`, and a missing or **unapproved** feature-request id answers `404 {"error": "Feature request not found"}` — the former `403` "Feature request is not approved" and "Public feature requests are disabled for this app" responses are gone, so a `403` from this route now means **only** Turnstile human-verification rejection. (The published spec documents one lumped `404` description over the generic `ErrorResponse`; these staged wire bodies are what the handlers emit.) Roadmap gate (PRIV-12): on a board with anonymous roadmap view disabled, an anonymous `POST` answers the uniform `401 {"error": "Sign in is required to view this roadmap", "code": "authentication_required"}` — even when anonymous voting is enabled — and the gate runs before the feature-request existence lookup, so missing and approved ids are indistinguishable and no `voteCount` is served; see [Per-App Anonymous-Access Enforcement (PRIV-12)](rate-limits-and-cache.md#per-app-anonymous-access-enforcement-priv-12). |
| `/api/v1/feature-requests/:id/vote` | `DELETE` | Explicitly remove the caller's vote — the only way to un-vote now that POST no longer toggles. Idempotent: removing a vote that is not present still answers `200` with the same `{voted: false, voteCount}` body, not an error. `voteCount` includes imported historical votes. The `DELETE` reads the **same JSON body as the POST**: `appKey` is always required, and the `userToken` follows the same body-or-`X-User-Token`-header rule with the body field winning (SaaS #834) — the published spec previously documented no body on this operation, so a spec-following client that sent none got the `400 Validation failed` above. Same per-client-IP vote rate limit applies (`429`). Existence hiding (SaaS #1165/#1171): an unknown `appKey` and a known app with public access disabled both answer `404 {"error": "App not found"}`, and a missing or **unapproved** feature-request id answers `404 {"error": "Feature request not found"}` — this operation previously documented neither `403` nor `404` for those cases (the published spec documents one lumped `404` description; these staged wire bodies are what the handlers emit). Body-size note (SEC-36): the JSON body is read through a 256 KB bounded reader **before** the vote rate limit, so an oversized body fails with `413 payload_too_large` instead of `429`. Roadmap gate (PRIV-12): on a board with anonymous roadmap view disabled, an anonymous `DELETE` answers the uniform `401 {"error": "Sign in is required to view this roadmap", "code": "authentication_required"}` — even when anonymous voting is enabled — and the gate runs before the feature-request existence lookup, so missing and approved ids are indistinguishable; see [Per-App Anonymous-Access Enforcement (PRIV-12)](rate-limits-and-cache.md#per-app-anonymous-access-enforcement-priv-12). |
| `/api/v1/feature-requests/:id/comments` | `GET` | List comments and @replies on a feature request. Keyset-paginated (PROD-31): pages walk `(createdAt, id)` oldest-first with `limit` 1–200 (default 200) and an opaque `cursor` from the previous page's `nextCursor`; returns `{comments, total, hasMore, nextCursor}` where `total` is the thread size under public visibility rules (hidden and deleted excluded — not `comments.length`) and `nextCursor` is `null` on the last page. Clients assuming one fetch returns the whole thread must walk `nextCursor`: the old silent 500-row cap is gone and every request returns at most 200 rows. A malformed cursor fails with `400 {"error": "Invalid cursor"}`. Sign-in-only boards (anonymous roadmap view disabled) answer `401` `authentication_required` to anonymous reads, and threads of **unapproved** requests return `404` — the same existence hiding as the board listing, so never infer "deleted" from a `404` (PRIV-12). Rate limited per client IP (`429`, shared 60/min public-read bucket); the thread body is identity-independent, so every `200` may be served from a 30-second shared cache — see [Public Board Read Limits and Shared Cache](rate-limits-and-cache.md#public-board-read-limits-and-shared-cache). |
| `/api/v1/feature-requests/:id/comments` | `POST` | Post a comment or @reply on a feature request. `parentId` must reference a **visible** comment on the feature request in the URL (not hidden, not soft-deleted, same request); any other parent id — one from a different feature request, app, or workspace, one that does not exist, or one that is hidden/deleted — is rejected with `400 {"error": "The comment you are replying to was not found on this feature request", "code": "invalid_parent"}` and nothing is stored (SEC-50). Corrected request schema `CreateFeatureRequestCommentInput` (SaaS #1117 / PR #1119): `body` max length is **2000** (the previously documented 4000 was wrong), and the author fields `authorName`, `authorEmail`, `authorAvatarUrl`, and `replyToClerkId` are removed from the schema — the server always derives author identity server-side and silently strips such request fields, so sending them is accepted but never stored; `parentId` and `replyToAuthorName` remain optional string fields, and `replyToAuthorName` in the request body is ignored: the replied-to author's display name (and `replyToClerkId`) is always resolved server-side from the parent comment. Authentication is the Clerk end-user session only — the route reads no `X-User-Token`, and the published spec no longer documents one for it (SaaS #834 dropped the decorative header parameter). Status codes (SaaS #1165/#1171): the shared submit limiter (`429`) and the 256 KB body budget (SEC-36) run first, then the Clerk gate answers `401 {"error": "Sign in is required to comment", "code": "authentication_required"}` **before** the lookup — an anonymous caller receives `401` regardless of the id — and a missing id, an id on an app with public access disabled, and an **unapproved** request all answer the same uniform `404 {"error": "Feature request not found"}` (existence hiding; the previously undocumented `403` "Only approved requests can be commented on" is gone). Success answers `201` with the `FeatureRequestCommentCreated` envelope `{ comment }` (SaaS #1105): `comment` is required and holds the full public `FeatureRequestComment` record inside the wrapper — **not** the bare record the spec previously referenced — so a strict client must unwrap `.comment` before rendering. |
| `/api/v1/me/link` | `POST` | Explicitly link an anonymous end-user profile to the signed-in Clerk identity (SEC-12). Requires the `X-User-Token` header plus a Clerk session; see [End-User Token Header & Identity Linking (SEC-12)](user-identity-and-privacy.md#end-user-token-header--identity-linking-sec-12). |
| `/api/v1/me/erase` | `POST` | Self-service data erasure (PRIV-01): erases the caller's own end-user profile for one app — rotates the anonymous token, clears stored PII, and anonymizes feature requests/votes/comments. Authenticates with the `X-User-Token` header or a Clerk session; see [Self-Service Data Erasure (PRIV-01)](user-identity-and-privacy.md#self-service-data-erasure-priv-01). |
| `/api/v1/users/:userId/profile` | `GET` | Public user profile, owned public apps, and recent comments (`PublicUserProfileResponse`: `{profile, publicApps, recentComments}`, all three keys required; `recentComments` is always emitted, `[]` when hidden or empty — never `apps` or top-level `hideComments`, SaaS #1190; see [User Identifiers on Public Endpoints (PRIV-06)](user-identity-and-privacy.md#user-identifiers-on-public-endpoints-priv-06)). `userId` must be an app-scoped pseudonym (`u_*`); pass `?appKey=` to resolve it. Since SaaS #1322 (issue #261) resolution is pseudonym-only: any non-`u_*` identifier — including raw Clerk `user_*` ids from legacy `/u/` links — answers the anonymous placeholder (`200`, `displayName: null`, empty `publicApps` / `recentComments`), never the opted-in profile. Unknown `u_*` ids return `404` without a reverse-lookup scan (SEC-34). Avatar fields (`profile.avatarUrl`, `recentCommenters[].avatarUrl`) are `null` or a managed `https:` URL — see [Profile Avatar URLs Are Managed-Host-Only (PRIV-19)](user-identity-and-privacy.md#profile-avatar-urls-are-managed-host-only-priv-19). Rate limited per client IP: 60 requests/minute in the same bucket as the `PUT .../user` upsert, `429` on bursts. |
| `/api/v1/feedback` | `POST` | Submit feedback draft with optional attachments. > **Changelog double opt-in flow (SEC-14 + SEC-35, as shipped):** `POST /changelog/subscribe` stores the address as *pending* and emails a single-use confirmation link. That link is a `GET /changelog/confirm?token=...` URL, but since SEC-35 **GET is strictly non-destructive** — it validates the token and renders an HTML interstitial whose form POSTs the token back; only `POST /changelog/confirm` consumes the token and flips the subscription to *confirmed* (browser form submissions with `Accept: text/html` get the HTML landing page; other clients get `{"confirmed": true}`). Email-scanner URL detonation (SafeLinks/Proofpoint) is therefore harmless for confirmation links: fetching the link leaves the subscription *pending* with the token intact, so links no longer need to be treated as single-shot or protected from prefetchers. The same interstitial pattern applies to unsubscribe (`GET .../unsubscribe?token=` is safe, only `POST` unsubscribes) and the weekly digest (PRIV-07). Responses across all three flows are uniform (no membership oracle). Unsubscribe is the exception to token expiry and to the private-app `403`: an authentic signature for that app is accepted after `exp` and when public surfaces are disabled (#635). Confirmation tokens are not. Rate budgets: subscribe, both confirms, and every GET share the per-IP `PUBLIC_WRITE_RATE_LIMITER` (10 requests/60 s); the one-click unsubscribe **POSTs** split off — a POST carrying the token in the query string draws from the dedicated `DIGEST_UNSUBSCRIBE_RATE_LIMITER` at 300 requests/60 s (PRIV-08, sized for mailbox providers that POST from shared egress IPs). The budget is chosen before the body is read, so a POST whose token arrives only in the body stays on the 10/min public-write bucket. Retry `429`s with exponential backoff. PRIV-12: on changelogs with anonymous access disabled, subscribe additionally requires a signed-in session bound to a verified address — see [Per-App Anonymous-Access Enforcement (PRIV-12)](rate-limits-and-cache.md#per-app-anonymous-access-enforcement-priv-12). Turnstile: when the server enforces human verification, anonymous subscribe bodies must also carry a valid `turnstileToken` or they answer `403` `turnstile_verification_failed` (signed-in verified-address callers are exempt) — see the subscribe row above.

> **Private-app config fail-closed (SEC-37):** both config routes return `404 {"error": "App not found"}` for private apps (`allowPublic = false`) — identical to the unknown-key response, so callers cannot distinguish the two and must treat 404 as "not found or not public". Do not expect a `200` body with `allowPublic: false`; only public apps get a `200 PublicAppConfig` (with `allowPublic: true`, schema unchanged). Since SaaS #1165/#1171 the roadmap surfaces split from the rest: the public columns and versions reads and every feature-request route (board listing/detail, vote, comment thread/create) answer the same uniform `404 {"error": "App not found"}` for a known app with public access disabled as for an unknown key (existence hiding — see the rows above), while the changelog feed keeps `403 {"error": "Public surfaces are disabled for this app"}` and feedback with its upload endpoints keep `403 {"error": "Public feedback is disabled for this app"}`. Changelog unsubscribe is the exception: a token whose signature matches the app still succeeds when public surfaces are disabled — see [Changelog Unsubscribe on Private Apps and After Expiry (#635)](email-subscriptions.md#changelog-unsubscribe-on-private-apps-and-after-expiry-635).

> **Public changelog pagination (PROD-28, `ListPublicChangelogResponse`):** `GET /api/v1/public/apps/:appKey/changelog` is keyset-cursor-paginated. Read `hasMore` / `nextCursor` from the response and pass `nextCursor` back as the `cursor` query parameter until `hasMore` is `false` (`nextCursor` is `null` on the last page). Treat the cursor as opaque — never parse, construct, or persist one beyond a forwarding step; malformed cursors return `400` `{"error": "Invalid cursor"}`. Entries are ordered newest-first, `limit` is clamped server-side to 1–100 (default 100), and keyset semantics keep an in-progress walk stable even if new entries are published mid-walk. Clients that only read `.entries` remain fully compatible. Anonymous reads of this feed may be served from a 30-second shared cache, so a publish can take that long to appear; a Clerk session bypasses the cache (see [Public Board Read Limits and Shared Cache](rate-limits-and-cache.md#public-board-read-limits-and-shared-cache)).

> **Public feature-request list pagination (DATA-01, `PaginatedFeatureRequests`):** `GET /api/v1/feature-requests` accepts an opaque keyset `cursor` over the `(createdAt DESC, id DESC)` order alongside the legacy `offset` parameter. The response always includes `hasMore` and `nextCursor` next to `requests`/`total` — `hasMore` is exact (the server fetches one extra row) and `nextCursor` is `null` on the last page. Walk large boards by starting without a cursor and echoing `nextCursor` back as `?cursor=` until it is `null`; a request that supplies `cursor` ignores `offset` entirely. Treat the cursor as opaque — never parse, construct, or persist one beyond a forwarding step; malformed cursors return `400` `{"error": "Invalid cursor"}`. `offset` above 10000 is clamped to 10000 and still returns `200` — it is not an error; deep pages belong on the cursor. The public showcase (`GET /api/v1/public/showcase` and its alias `GET /api/v1/public/apps`) clamps `offset` at 5000 the same way. `total` is computed for the current filters independently of the cursor, so it stays constant across pages; `limit` stays clamped to 1–200 (default 50), and `q`/`versionId` filters compose with cursor paging. Keyset semantics keep an in-progress walk stable even when new requests are submitted mid-walk, and clients that only read `requests`/`total` remain fully compatible.

Each public feature request's `voteCount` is the displayed total: in-app votes plus historical votes imported from the source provider. The optional `importedVotes` field reports only that historical portion; it is already included in `voteCount` and is `0` for requests created in CupThread. Both `GET /api/v1/feature-requests` (board listing/search) and `GET /api/v1/feature-requests/{id}` (request detail) serve only the documented public `FeatureRequest` schema (SaaS #1320 / PR #1323): ten undocumented tenant-internal keys previously leaked as `null` — `importSource`, `importRef`, `githubIssueId`, `githubIssueNumber`, `githubIssueUrl`, `githubDiscussionId`, `githubDiscussionNumber`, `githubDiscussionUrl`, `githubLastSyncedAt`, and `githubSyncStatus` — are never served on public surfaces (drop them from any SDK or client model that declared them; `importedVotes`, `voteCount`, `hasVoted`, `isOwnRequest`, and the column/version fields remain unchanged).
